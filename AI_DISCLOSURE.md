# AI Disclosure

This project uses AI in three distinct ways. Each is listed with what it did and how its output was checked.

## 1. AI-assisted development

The repository was developed with **Claude Code** (Anthropic's agentic coding assistant), working under the
direction of the team. Its work covered:

* the code, tests, benchmark scripts and documentation;
* the synthetic development fixture.

The commits are authored under the team's account; this file is the record of how AI was involved. Most of
the code, tests and documents were written by the assistant and reviewed and directed by the team.

How the AI-written work was checked:

* **Tests.** More than 360 offline tests: unit, integration, sample-regression and adversarial (`make test`).
* **Live evaluation.** Every number in `metrics.md` was measured by scripts against a real server and a real
  model, then rendered from the JSON reports. No figure was typed by hand.
* **Hostile review.** The issues found and fixed are listed in `HARDENING_REPORT.md`.
* **Traceability.** `REQUIREMENTS_TRACEABILITY.md` links every requirement to its implementation, test and
  evidence. Targets that are not fully met are marked *Partial* or *Not met*, not hidden.

## 2. AI models used at run time (inside the product)

| Purpose | Model | Where |
| :--- | :--- | :--- |
| Structure extraction: SIIS reference text → goal, actions, steps | Large language model via API. Reported numbers: Google Gemini `gemini-3.1-flash-lite` (default, with fail-over chain); an earlier run with Groq `openai/gpt-oss-120b` is archived | `app/services/structure_extraction.py`, `app/llm/` |
| Query paraphrases (`query_variations`) | the extraction model (Gemini), or a dedicated model such as Groq `openai/gpt-oss-20b` | `app/services/troubleshooting.py` |
| Semantic retrieval and cache matching | `BAAI/bge-small-en-v1.5` sentence embeddings, run locally (ONNX via fastembed) | `app/retrieval/embeddings.py` |
| Full-LLM deeplink mapping | LLM; **ablation baseline only**, not used in production | `app/services/deeplink_mapping.py` (`DEEPLINK_MAPPER=llm`) |

The model is an assistant, not the controller. Code enforces every hard rule, whatever the model outputs:

* **Grounding.** Steps must be grounded in the supplied text; invented steps are removed.
* **Deeplinks.** URIs are copied from the catalog registry, never from model output.
* **URL scrubbing.** Every field is checked for URLs and pseudo-links.
* **Ordering.** Categories and critical-last sequencing are deterministic rules.
* **Validation.** Every response passes the `schema.py` contract and the business-rule gates before it is
  returned or cached.

## 3. AI-generated data

* **Official data.** `data/official/` holds the organisers' starter files unchanged (`input.txt`,
  `siis_responses.json`, `deeplinks.json`, `schema.py`, `sample_output.json`); `queries.json` and the sample
  file only re-package them. None of it is AI-generated by the team.
* **Team-written evaluation inputs.** `data/official/eval/negatives.json` and `edge_cases.json` were written for
  the official knowledge base with AI assistance and are labelled as such.
* **Held-out paraphrases.** `data/official/eval/paraphrases_llm_heldout_r2.json` and `_r3.json` were generated by
  `qwen/qwen3.8-27b` on Groq (a few by the `openai/gpt-oss-20b` fallback), a different model family from the one
  that wrote the cache keys. Round 3 was generated after the last change to query enrichment, so it is the
  reported hit rate.
* **Development fixture.** `data/dev_fixtures/` is synthetic: it is not official Samsung data, and every file
  says so. It was written with AI assistance before the official data was available, together with its gold
  labels and LLM-generated paraphrases (Gemini models).

The development fixture and the system were produced in the same project, so the fixture's accuracy numbers
(archived in `artifacts/reports/dev_fixtures/`) are optimistic; the official-data numbers in `metrics.md` are the
ones to use.
